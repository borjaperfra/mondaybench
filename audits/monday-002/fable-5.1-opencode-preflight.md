# Preflight: Claude Fable 5.1 via OpenCode — NO-GO

**Date:** 2026-09-02
**Runtime under test:** OpenCode 1.18.14 (`~/.opencode/bin/opencode.exe`)
**Operator:** Claude Code (this session), never the runtime under test
**Scenario:** monday-002, frozen. Not executed. No official runs, no leaderboard change.

Raw evidence: `fable-5.1-opencode-wire-capture.json` (this directory).

---

## 0. A correction that has to come first

**MondayBench has never used OpenCode for anything.** `grep -rli opencode`
across the whole repository returns zero files. Every official run in
`runs/` was generated by `mondaybench run` →
`mondaybench/runner.py:127 build_model_provider(model)` →
`mondaybench/providers/openai_compatible.py` → httpx straight to the gateway.

The reason OpenCode *looks* like it was involved is that the user's global
`~/.config/opencode/opencode.json` happens to declare `helmcode` and `nan`
providers with three of the same models. That is a coincidence of the operator's
own tooling, not the benchmark's generation path.

So there is no "same method as the other benchmarks" to reuse here. The method
the other benchmarks used is the direct httpx call, and its exact payload is
reproduced in §6 below as the comparison baseline.

## 2. Authentication — STOP

    opencode run -m anthropic/claude-fable-5-1 "Reply with exactly: FABLE_OK"
    -> ProviderModelNotFoundError: Model not found: anthropic/claude-fable-5-1

The model is in the catalog but the provider is never constructed, because no
Anthropic credential exists. Three independent confirmations:

1. `auth.json` holds two credentials, `helmcode` and `nan`, both `type: "api"`.
   No `anthropic` key of any type. Verified unchanged afterwards — sha256
   `9100c337a59a28a6ccc37e6383deff5a671f5f8ac9565e42210dda3afe0fc272`.
2. The catalog declares `ANTHROPIC_API_KEY` as the credential for this provider.
3. `opencode models anthropic` → `Provider not found: anthropic`.

**Can OpenCode use a Claude subscription in principle?** Partly answered, and
worth stating precisely rather than guessing. The binary contains the UI strings
for it — `provider.connect.title.anthropicProMax` = "Sign in with Claude
Pro/Max", alongside method labels `apiKey` / `browser` / `headless`. But the
binary contains **no Anthropic OAuth endpoint**: the OAuth authorize/token URLs
present are Google, `auth.openai.com`, `auth.x.ai`, DigitalOcean, Poe and
GitLab. No `claude.ai`, no `console.anthropic.com`. So the login method is
advertised in the interface and its endpoint is not in this build — most likely
supplied by a provider-auth plugin resolved at runtime.

Provisioning it was **not attempted**: it means running
`opencode providers login`, which writes a credential, and the instruction was
explicitly not to modify auth or install third-party plugins. One probe with an
invalid method label hung on an interactive prompt and was killed; `auth.json`
was verified byte-identical afterwards.

**This is where the Anthropic path stops.** Everything below is the other half
of the question, and it is the half that decides whether provisioning that
credential would be worth doing at all.

## 3. Wire capture — what OpenCode actually sends

Asking the model to repeat its own system prompt was explicitly the least
preferred method, so it was not used. A local forwarding proxy was placed
between OpenCode and the gateway, logging every request body verbatim and
redacting the `Authorization` header to its length.

Because OpenCode has no Anthropic credential, the capture ran on
`helmcode/qwen3.6`. **The injection under test is a property of the OpenCode
harness, not of the provider** — the system prompt, tool set, env block and
sampling fields are assembled by OpenCode before any provider adapter is
reached. Two caveats stated rather than hidden: a hypothetical Anthropic adapter
could add provider-specific fields on top of what was captured, and it could
carry the same content in the Messages API shape instead. Neither could
plausibly *remove* what is below.

OpenCode issued **two** requests for one prompt.

### Primary agent call

    model            qwen3.6
    temperature      not sent
    top_p            1
    max_tokens       32000
    stream           true
    tool_choice      auto
    tools            bash, edit, glob, grep, read, skill, task,
                     todowrite, webfetch, write        (10 definitions)
    messages         2  (system 13,710 chars; user 30 chars)

The 13,710-character system prompt contains, verbatim:

    You are opencode, an interactive CLI tool that helps users with software
    engineering tasks. ...

    You are powered by the model named qwen3.6. The exact model ID is helmcode/qwen3.6
    Here is some useful information about the environment you are running in:
    <env>
      Working directory: ...\scratchpad\ocprobe
      Workspace root folder: ...\scratchpad\ocprobe
      Is directory a git repo: yes
      Platform: win32
      Today's date: Wed Sep 02 2026
    </env>

…followed by an `<available_skills>` catalog that enumerates the operator's own
**Claude Code** skills from `~/.claude/skills/`, each with name, description and
absolute filesystem path: `customize-opencode`, `frontend-design`,
`get-tsconfig`, `making-a-helmcode-model-card`, `making-a-nan-social-card`,
`publishing-a-post`, `sending-a-newsletter-issue`. It also instructs the model
about `AGENTS.md`, about `<system-reminder>` tags, and about batching `git
status` calls.

### Auxiliary harness call

A second request, no tools, 2,096-character system prompt, same model, same
`top_p: 1`. OpenCode makes its own extra model call per turn — structurally the
same overhead as Claude Code's `claude-haiku-4-5` side call.

### Classification

| Element | Class |
|---|---|
| `Today's date: Wed Sep 02 2026` | **D — new contamination, breaks comparability** |
| `You are opencode, an interactive CLI tool…` identity | **D** |
| 10 tool definitions + tool-usage policy | **D** |
| `<available_skills>` catalog of the operator's Claude Code skills | **D** |
| `<env>` working directory / workspace root / git-repo flag / platform | **D** |
| `AGENTS.md` and `<system-reminder>` instructions | **D** |
| "You are powered by the model named …" self-identification | **D** |
| `top_p: 1` sent | **D** (the official runs pin no `top_p`) |
| `temperature` not sent | B — correct for this family, and already documented |
| second auxiliary model call | C-adjacent — harness overhead, absent from the official runs |

Nothing lands in class A. Not one element of the injected context is common to
the seven models already on the monday-002 board, because those runs went
through a payload builder that sends nothing but the frozen system prompt and
the frozen user prompt.

## 4–5. Canary and temporal probes — not run, and why

Both were made redundant by §3. The canary probe was designed to discover
whether a supplied system prompt is replaced or concatenated, and whether a date
is injected. The wire answers both directly and more reliably: OpenCode composes
its own system prompt around the agent identity and the `<env>` block, and
`Today's date: Wed Sep 02 2026` is inside it.

The temporal test's own stated failure condition is therefore already met.
monday-002 declares `current_time: 2026-09-14T09:07:00+02:00`; OpenCode delivers
`Wed Sep 02 2026` in the system prompt. A model would receive the scenario date
and the real date simultaneously — **FAIL for MondayBench regardless of whether
it answers correctly**, which was the criterion given.

Running the two extra probes would have spent tokens to re-confirm a fact
already on the wire.

## 8. Execution chain actually observed

    operator   Claude Code (this session)
      ->       Bash: `opencode run -m <provider>/<model> …`
      ->       OpenCode 1.18.14, own process, own agent loop
      ->       local capture proxy 127.0.0.1:8899
      ->       https://api.helmcode.com/v1  (helmcode credential from OpenCode's auth.json)
      ->       qwen3.6

Confirmed by: separate process invocation; OpenCode's own stdout/stderr
(`llm.runtime=ai-sdk llm.provider=helmcode llm.model=qwen3.6`); the captured
wire bodies; and the system prompt in which the runtime names itself as
opencode. Claude Code never answered on the model's behalf at any point.

The chain that was *wanted* — `… -> OpenCode -> Anthropic subscription ->
claude-fable-5-1` — was never established, because the third hop does not exist
on this machine.

---

## 9. Reason, in five sentences

OpenCode 1.18.14 does list `claude-fable-5-1` in its catalog, but it has no
Anthropic credential, its catalog names `ANTHROPIC_API_KEY` as the only
credential for that provider, and this build contains no Anthropic OAuth
endpoint at all — so the call fails before any request is made, and provisioning
it was out of scope. More importantly, a wire capture shows OpenCode would not
help even with the credential: it composes its own 13,710-character system
prompt containing an opencode identity, ten tool definitions, an `<env>` block
with the working directory and git status, a catalog of the operator's Claude
Code skills, and `Today's date: Wed Sep 02 2026`. That last item is the same
conflicting-date contamination that blocked Claude Code, against a scenario
whose `current_time` is 2026-09-14 and whose largest scoring dimension is
temporal supersession. Against the preserved official payload — a 28-character
system prompt, the frozen user prompt, no tools, no date — message count and
order are the only dimension that matches. OpenCode is therefore not a cleaner
runtime than Claude Code for this purpose; it is a substantially dirtier one,
and the gateway route remains the only path to a comparable monday-002 row.
