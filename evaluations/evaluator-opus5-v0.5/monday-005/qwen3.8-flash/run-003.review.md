### What happened

- **11:31 UTC** — Release `batch-api@2026.11.09-r3` finished rolling out to both Batch API worker fleets. The changeset included lowering the batch worker database connection-pool ceiling from **80 to 24 per worker**.
- **11:38 UTC** — Batch submission volume on **fleet-a** began climbing, driven mainly by `wonka-industries` starting a large scheduled job. By 11:50 UTC it was roughly **3x** the morning average on that fleet.
- **11:42 UTC** — Incident start. `batch_api_5xx_rate` crossed its page threshold on fleet-a. Errors were **502** responses on `POST /v1/batch/jobs`.
- **11:44 UTC** — Errors were confirmed as confined to fleet-a. fleet-b was serving normally.
- **11:47 UTC** — Upstream object-storage provider was ruled out: provider status was green, and the Files API, which uses the same provider, remained healthy.
- **12:03 UTC** — Marcus observed fleet-a workers queueing on database connections and noted the timing correlation with the `r3` pool-size change. This was **not tested**.
- **12:31 UTC** — Decision: do **not** roll back `r3` yet, because rollback would remove evidence needed to test whether the pool change is responsible. Mitigate by moving traffic instead.
- **12:58 UTC** — Mitigation applied: all Batch API traffic was cut over to fleet-b. fleet-a was drained and held out of rotation. Error rate on `POST /v1/batch/jobs` fell to **0.4%** within two minutes; baseline for the endpoint is **0.2%**.
- **13:00 UTC** — Verification window opened. It closes at **14:30 UTC**. Northstar policy requires **90 minutes** of continuous normal error rate on the affected endpoint before declaring resolution.
