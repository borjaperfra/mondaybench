## CEO BRIEFING

**Incident:** INC-2026-1109-01  
**Time of this briefing:** 14:20 UTC, Monday 9 November 2026  
**Current state:** OPEN — mitigated, verification in progress, root cause not established.

### What happened

- At **11:31 UTC**, release `batch-api@2026.11.09-r3` finished rolling out to both Batch API worker fleets. The changeset included a database connection-pool change: max pool size lowered from **80 to 24 per worker**.
- At **11:38 UTC**, Batch submission volume on **fleet-a** began climbing, reaching roughly **3x the morning average**, driven mainly by `wonka-industries` starting a large scheduled job.
- At **11:42 UTC**, the first page fired: `batch_api_5xx_rate` crossed threshold on **fleet-a**. Errors were **502 responses on `POST /v1/batch/jobs`**.
- At **11:44 UTC**, engineering confirmed the errors were confined to **fleet-a**. **fleet-b** was serving normally with no elevated error rate.
- At **11:47 UTC**, the upstream object-storage provider was ruled out: its status page was green, and the Files API, which uses the same provider, stayed healthy.
- At **12:03 UTC**, engineering noted that fleet-a workers were queueing on database connections and correlated that with the `r3` pool-size change. This is a hypothesis, not a confirmed cause.
- At **12:31 UTC**, the decision was made **not to roll back `r3` yet**, because rolling back would remove the evidence needed to test whether the pool change was responsible. The same release was running on fleet-b without harm.
- At **12:58 UTC**, mitigation was applied: **all Batch API traffic was cut over to fleet-b**. fleet-a was drained and held out of rotation.
- Error rate on `POST /v1/batch/jobs` fell to **0.4% within two minutes**. Baseline for that endpoint is **0.2%**.
- At **13:00 UTC**, the verification window opened. Incident policy requires **90 minutes of continuous normal error rate** on the affected endpoint before the incident can be declared resolved. The window closes at **14:30 UTC**.
- At **14:12 UTC**, error rate was **0.3%**, queue depth on fleet-b was normal, and there were no customer reports of new failures since the cutover.
- At **13:52 UTC**, re-drive of failed jobs was roughly **60% complete**, with no failures on re-drive.

### Impact

The headline impact figure is failed Batch API requests as a share of all Batch API requests in the incident window, computed from `customer-impact.csv`.

- Batch API requests in the incident window: **58,900**
- Failed Batch API requests in the incident window: **17,602**
- Failed Batch API requests as a share of Batch API requests: **29.9%**

For context, Northstar served **842,000 platform-wide requests** across all API surfaces between 11:42 and 12:58. The Batch API share of that total is **58,900 requests**, or about **7.0%** of platform-wide traffic in the window.

### Root cause status

Root cause is **not established**.

Two candidate explanations remain live and untested:

1. **H1 — connection-pool change in `r3`**
   - For: `r3` lowered max pool size from 80 to 24 per worker and shipped at 11:31, eleven minutes before the first page; fleet-a workers were observably queueing on database connections.
   - Against: `r3` shipped to fleet-b too, and fleet-b never degraded.
   - Status: untested. The rollback test has not been run.

2. **H2 — concentrated load on fleet-a**
   - For: fleet-a was at about 3x its morning average from 11:38, driven by one large scheduled job.
   - Against: fleet-a absorbed a higher peak on 2026-11-03 without elevated errors.
   - Status: untested.

They may interact — a lower pool ceiling would bite hardest under higher concurrency — but that interaction has not been tested.

A third candidate, the upstream object-storage provider, was rejected at 11:47.
