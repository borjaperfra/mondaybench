# Generation incident: duplicate generation of monday-004 run 1

**Date:** 2026-09-02
**Affected slot:** `raw/monday-004-run1.json`
**Outcome:** the run on disk is kept. No run was invalidated, no run was
selected on quality, and no fourth generation was produced.

## What happened

The generation script was first launched over the full 15-run target list as a
background process (started 13:32:57). Partway through, that process appeared to
have died: no `python.exe` was visible in the task list and the log had not been
written to for four minutes. Working on that reading, monday-004 run 1 was
launched again in the foreground.

The first process had not died. It was between runs, and it went on to generate
monday-004 run 1 and run 2. Both processes therefore generated run 1, and the
file was written twice. The second write won.

Two generations of one run slot existed; one survives.

## What survives, and what was lost

The file on disk is the foreground generation:

    response_chars   17,143
    output_tokens    23,925
    reasoning_tokens 16,854
    ttfa_ms          207,419
    session_id       08f9571b-cb42-4a8e-9f97-d9d4317cbc39
    generated_at     2026-09-02T11:52:25Z

The overwritten generation survives only as its log line, which is reproduced
here in full because it is the only remaining evidence of it:

    OK   monday-004 run1  21856ch  out=24227 think=15516 ttfa=189098.4 stop=end_turn 305s

Its response text is gone. It was never read and never judged.

## Why this is not an invalidation

Checked against the replacement policy for this experiment. None of the
invalidation causes applies to the surviving run:

| Cause | Present? |
|---|---|
| provider failure | no |
| truncated response caused by infrastructure | no - `stop_reason: end_turn` |
| reasoning requested but not delivered | no - 16,854 thinking tokens |
| malformed or incomplete transport | no - complete JSON, full usage block |
| wrong model served | no - `claude-opus-5`, `firstParty` |
| wrong prompt sent | no - `prompt_sha256` matches the frozen hash |
| configuration mismatch | no - same flags, same ceiling, same route |

The surviving run is a valid generation under the correct configuration.

## Why the surviving run was not "chosen"

This is the part that matters, because picking the better of two generations is
exactly what the run policy forbids.

The selection was made by filesystem write order at 13:52, at a point when
**neither response had been read and neither had been judged**. No score, no
label and no criterion existed for either generation. Write order is not
correlated with quality, so the retention is arbitrary in the harmless sense
rather than selective in the forbidden sense.

Note also that the discarded generation's observable metadata was *larger* on
two of three axes - 21,856 characters against 17,143, and 24,227 output tokens
against 23,925 - so nothing about the surviving choice trends toward a more
favourable result. On this scenario length is not quality, but it does rule out
the reading that the shorter, tidier response was kept on purpose.

## Why no fourth generation was produced

Regenerating run 1 cleanly was considered and rejected. It would have produced a
third generation of the same slot and required choosing between three rather
than two, which is a worse position, not a better one - and the run policy for
this experiment is explicit that the three predefined runs count and that a run
is replaced only for an objective methodological cause. There is no such cause
here.

## What was changed to stop it recurring

The duplicate process was killed (PowerShell `Stop-Process`; `pkill` matches
nothing on this machine) and the remaining runs were generated by a single
process. Process liveness was confirmed with `Get-Process` rather than inferred
from log inactivity, which is what produced the false "it died" reading in the
first place.
